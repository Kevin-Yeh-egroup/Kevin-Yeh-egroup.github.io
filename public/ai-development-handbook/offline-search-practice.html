做一個你想用的功能

想讓搜尋更好用，或加一個常用的按鈕？跟著這 12 關，把點子說給 AI 聽，做出一個可以親手試的小版本。

  1. 說清楚想改什麼
  2. 用 AI 做出一小版
  3. 親手測試
  4. 交給團隊審查

先用練習資料做一次。最後帶上你自己的點子，和 Kevin 及隊友一起看怎麼加進團隊系統。

卡在一個名詞？翻小字典

想到哪個就查哪個。可以打中文，也可以直接貼上看到的英文字。

AI 助手（Codex／Claude）
可以先把 AI 當成一位搭檔。Codex 可以照你的要求讀程式、試改和跑測試。Claude 可以先畫給你看，也能幫忙找漏掉的地方。
舉個例子：你說「搜尋前後有空白也要找得到」，再親手確認結果。
專案（Project）
做一個工具需要的程式、資料和說明，放在同一個地方。
舉個例子：Kevin 給你的練習資料夾，就是你這次做小工具的地方。
Node.js／LTS
這門課要用 Node.js 在你的電腦上跑搜尋練習和檢查。裝好後，Codex 才能幫你跑這份練習的測試，告訴你改完有沒有修好。純聊天、寫工單或看教材時，還用不到它。
舉個例子：搜尋「入門」前後多了空白，本來找不到課程。修好後，請 Codex 用 Node.js 再跑一次，看同一筆輸入能不能找到「程式入門」。下載頁的 LTS 是長期支援版。團隊專案有指定版本時，就照專案說明安裝。
終端機（Terminal／PowerShell）
可以用打字叫電腦做事的視窗。Windows 的 PowerShell 就是其中一種。
舉個例子：輸入 node --version，是請電腦告訴你裝了哪個版本。
Git／GitHub
Git 幫你記錄程式改了哪裡。GitHub 是團隊放程式、討論改動和請人審查的網站。
舉個例子：在自己電腦存一筆 Git 紀錄。等對方確認可以送出，再放到 GitHub。
程式庫（Repository／Repo）
一個專案的檔案和修改紀錄放在一起的地方。
舉個例子：Kevin 傳來的 GitHub 練習專案連結，通常會帶你到 repo。
工單（Issue）
一張寫清楚想改什麼、怎麼重現和怎樣算做好的工作單。
舉個例子：「貼上前後有空白的『入門』也要找到課程」比「搜尋怪怪的」好懂。
分支（Branch／main）
分支是從某一版開出來的工作線。團隊常把主要版本叫 main。
舉個例子：把搜尋修改放在這張工單的分支上，團隊可以先看過。
存一版（Commit）
把這次挑好的改動存成一筆版本紀錄，順便寫一句改了什麼。
舉個例子：例如「讓搜尋忽略前後空白」。之後能找到這次改過哪些檔案。
送到 GitHub（Push）
把你電腦上的版本紀錄送到 GitHub，讓隊友也看得到。
舉個例子：先確認要送到哪個專案和分支，再依團隊授權送出。
審查頁（Pull Request／PR／Draft PR）
PR 是給隊友看這批改動的頁面。Draft PR 還在準備中。
舉個例子：你可以放工單、測試結果和畫面，請 IT 幫忙看空查詢的結果。
合併／部署（Merge／Deploy）
合併是把通過審查的改動接回團隊的版本。部署是把某個版本送到大家實際使用的環境。
舉個例子：團隊把修改合進主版本後，會依流程決定何時讓使用者用到。
測試／自動檢查（Test／CI）
測試是照一個方法確認結果。CI 可以在 GitHub 自動跑團隊設定的檢查。
舉個例子：先用同一個輸入試兩次。一開始找不到課程，修完後找得到。
重現／驗收
重現是照相同步驟再看一次問題。驗收是依約好的結果親手試，確認這次做對了。
舉個例子：一開始先搜帶空白的『入門』，修完後再用同一個輸入檢查。
README
專案附的使用說明，通常會寫怎麼開起來、怎麼試。
舉個例子：關掉練習工具，再照 README 自己打開一次。
AI 分工（Agent）
把不同工作分給不同的 AI，說清楚各自要看什麼、交什麼、何時停。
舉個例子：Codex 改檔，Claude 只看差異、找漏測的地方，最後由你確認。

GitHub 通行證｜走到送審再用

為什麼要準備？ GitHub 是團隊放程式和討論修改的地方。你想把修改交給隊友看時，會在這裡開一張審查草稿。

哪一關會用到？ 第 8 關要把草稿送到 GitHub 時才需要。只在本機練習，可以先寫草稿。

  1. 已有團隊帳號就直接登入。需要新帳號時，到 GitHub 註冊，並到信箱完成驗證。公司提供的受管理帳號，依公司流程辦理。
  2. 接受組織或練習專案的邀請，再打開 Kevin 給你的連結。可以看專案後，請 Kevin 核對你是否能開工單、推分支和開 PR。

怎麼知道準備好了？ 你用自己的帳號開得了練習專案。能開啟連結和能送出修改是兩件事，送出前還要確認權限。

把工作方式告訴 Codex

小魔王 · 搶快怪　事情還沒說清楚，AI 就要動手。先跟它約好：看現況、等你開口，再開始改。

常駐工作指令（整段貼給 Codex）

看完整內容
你是我的 AI 開發搭檔。用繁體中文協作，我負責需求、實際驗收與發布決定，你負責有授權的查找、修改、驗證與交接。

收到這段後，直接開始唯讀健檢。回報目前資料夾、Git remote（遮蔽憑證）、分支、工作區是否有未提交變更、讀到的 AGENTS.md 與 README，以及可用的啟動與驗證指令。若這裡沒有 Git 或專案，指出原因並建議最小下一步。這一步做完就等我指定第一張任務。

收到任務後：
1. 核對專案規則及 Issue。用一句話重述目標，寫下可觀察的驗收條件。需求明確就往下做。遇到會改變需求、權限不足或會覆蓋他人工作時，提出最需要我決定的一個問題。
2. 依專案規則確認 Issue 後，從最新指定基底建立對應分支。正式專案缺 Issue 時先擬草稿，收到建立授權才發到 GitHub。若團隊採工單分支規則，就從最新 origin/main 開 issue/<編號>-<短名稱>，優先使用獨立 worktree。
3. 涉及正式 UI、操作流程或使用者體驗時，先核對已有的確認稿。需要新稿時，準備交接給正確專案的本機 Claude Code，帶入共用產品體驗標準，取得可渲染稿與人員確認，再做正式實作。Claude 與 Codex 依序接手，同一時間只有一個人或工具寫入工作副本。
4. 維持小改動，沿用既有實作。執行與變更相稱的檢查，記下命令、結果、失敗或跳過原因。UI 依實際操作路徑驗收，使用測試或去識別資料。
5. 按授權與專案規則建立本機 commit，只納入本次檔案。回報 Issue、分支、commit、改動摘要、驗收結果和預覽證據。
6. 外部建立 Issue、push、開 PR、設為 Ready、外部通知、merge 與部署，依目前授權及專案規則辦理。沒有授權時只準備草稿。若團隊採預覽確認流程，push／開 PR 前先交預覽並取得對應確認，預設 Draft PR。檢查 PR head、CI、mergeability 及畫面證據，Ready 與通知 IT 依團隊流程。通知前核對對象、管道與內容，缺資料時先備通知稿。
7. 遇到錯誤先查原因並在授權內修復。使用官方登入流程，避免讀出或傳送密鑰及個資。交接時列出可重現證據和還需人員決定的事項。

任務格式：專案／Issue、我想改什麼、如何驗收、這次允許你做到哪一步。若我只提供目標，先查現況並在已授權範圍內推進。

  1. 用同一個方法比較改前改後
  2. 從空資料夾做出可操作的小工具
  3. 分工複核並提出自己的功能工單

你可以把小版本、畫面和測試交給團隊，一起確認怎麼加進正式系統。

想把自己的點子加進團隊系統？把工單草稿、修改前後的畫面與測試結果交給 Kevin，和團隊確認怎麼審查與合併。

完成紀錄存在目前的瀏覽器。換裝置或清除瀏覽資料後，可以從第 1 關再練一次。
