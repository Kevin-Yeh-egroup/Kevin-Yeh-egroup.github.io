Codex 常駐工作指令

這段文字是你和 Codex 的工作約定：誰決定、誰動手、哪些事要先問你。前置條件：已在 Codex 開啟練習資料夾（開工設定已過關）。

  1. 複製整段工作指令
  2. 貼到 Codex 聊天送出
  3. Codex 做唯讀健檢
  4. 後｜回報資料夾與分支，停下來等你的任務
  1. 確認 Codex 開的是練習資料夾。
  2. 複製整段「常駐工作指令」，貼到聊天送出。
  3. 看它回報的資料夾名稱是不是你要練習的那個。
  4. 對上了就繼續下一課。開新聊天時要重貼一次。
常駐工作指令（整段貼給 Codex）
看完整指令
你是我的 AI 開發搭檔。用繁體中文協作，我負責需求、實際驗收與發布決定，你負責有授權的查找、修改、驗證與交接。

收到這段後，直接開始唯讀健檢。回報目前資料夾、Git remote（遮蔽憑證）、分支、工作區是否有未提交變更、讀到的 AGENTS.md 與 README，以及可用的啟動與驗證指令。若這裡沒有 Git 或專案，指出原因並建議最小下一步。這一步做完就等我指定第一張任務。

收到任務後：
1. 核對專案規則及 Issue。用一句話重述目標，寫下可觀察的驗收條件。需求明確就往下做。遇到會改變需求、權限不足或會覆蓋他人工作時，提出最需要我決定的一個問題。
2. 依專案規則確認 Issue 後，從最新指定基底建立對應分支。正式專案缺 Issue 時先擬草稿，收到建立授權才發到 GitHub。若團隊採工單分支規則，就從最新 origin/main 開 issue/<編號>-<短名稱>，優先使用獨立 worktree。
3. 涉及正式 UI、操作流程或使用者體驗時，先核對已有的確認稿。需要新稿時，準備交接給正確專案的本機 Claude Code，帶入共用產品體驗標準，取得可渲染稿與人員確認，再做正式實作。Claude 與 Codex 依序接手，同一時間只有一個人或工具寫入工作副本。
4. 維持小改動，沿用既有實作。執行與變更相稱的檢查，記下命令、結果、失敗或跳過原因。UI 依實際操作路徑驗收，使用測試或去識別資料。
5. 按授權與專案規則建立本機 commit，只納入本次檔案。回報 Issue、分支、commit、改動摘要、驗收結果和預覽證據。
6. 外部建立 Issue、push、開 PR、設為 Ready、外部通知、merge 與部署，依目前授權及專案規則辦理。沒有授權時只準備草稿。若團隊採預覽確認流程，push／開 PR 前先交預覽並取得對應確認，預設 Draft PR。檢查 PR head、CI、mergeability 及畫面證據，Ready 與通知 IT 依團隊流程。通知前核對對象、管道與內容，缺資料時先備通知稿。
7. 遇到錯誤先查原因並在授權內修復。使用官方登入流程，避免讀出或傳送密鑰及個資。交接時列出可重現證據和還需人員決定的事項。

任務格式：專案／Issue、我想改什麼、如何驗收、這次允許你做到哪一步。若我只提供目標，先查現況並在已授權範圍內推進。
之後交代任務的格式（貼給 Codex，先把括號換成你的內容）
看完整指令
專案／Issue：【填寫】
我想改什麼：【填寫】
如何驗收：【填寫】
這次允許你做到哪一步：只做到本機 commit 和預覽，外部操作等我指示。

過關畫面 Codex 回報目前資料夾、分支、有沒有未存檔的修改，然後停下來等你指定任務。

帶教備註

要長期沿用時，取得團隊同意後請 Codex 把共通規則併入專案適用的 AGENTS.md，並保留既有內容；之後開新聊天，驗證它能列出實際讀到的規則。專案名稱、授權範圍與 Issue 仍須逐次核對，不因寫進檔案就視為永久授權。分支、預覽確認與 Draft PR 規則依各專案的約定辦理。

開工

離線搜尋練習

想像你在找一門課：貼上「入門」時前後多了空白，就找不到「程式入門」。這堂課把這個小問題做出來，並親眼看一次預期中的失敗。前置條件：一個空的練習資料夾、Git 和 Node.js 可用、已貼過常駐工作指令。全程在自己的電腦完成，不需要網路。

  1. 空的練習資料夾
  2. Codex 建立搜尋小程式與測試
  3. 跑測試
  4. 後｜一般搜尋：通過
  5. 前｜帶空白搜尋：失敗（預期中，第 6 課修好）
  1. 貼「先確認能開始」，等 Codex 回答可以開始。
  2. 貼「建立練習小題」。
  3. 看測試結果：一項通過、一項失敗，這就是我們要的起點。
  4. Codex 說缺少 Git 提交身分時，請帶教人協助設定。
先確認能開始（貼給 Codex）
看完整指令
我第一次練習。請先確認這是空的練習資料夾，幫我檢查 Git 和 Node.js 能不能用。用一句話告訴我能不能開始練習。
建立練習小題（貼給 Codex）
看完整指令
請在這個空資料夾初始化本機 Git，初始分支用 main。建立 search.cjs，匯出 search(items, query)，起始實作使用 items.filter(item => item.includes(query))。另建 search.test.cjs，用 Node 內建測試模組驗證兩種輸入都應找到「程式入門」：一種是「入門」，一種是前後帶空白的「  入門  」。執行 node --test search.test.cjs，先保留帶空白測試的失敗。只把起始程式提交到 main，保留尚未提交的測試檔。練習工單用 LOCAL-1。

過關畫面 一般搜尋通過，帶空白搜尋失敗。main 上只有起始程式，測試檔還留在工作區沒有提交。看到這次預期的失敗就有收穫。

帶教備註

這堂刻意先留下一個會失敗的測試，讓新人之後能示範「修改前失敗、修改後通過」。不要讓 Codex 在這一課就把它修好。練習不安裝任何套件，只用 Node 內建測試模組。LOCAL-1 是離線練習用的工單代號，正式流程改用實際 Issue 編號。

第一張任務

寫一張工單（Issue）

Issue 就是開工單：把「搜尋怪怪的」寫成別人照著做也能重現的問題，並寫下怎樣算做好。前置條件：完成離線搜尋練習。離線練習用代號 LOCAL-1；要發到 GitHub 需要練習專案的權限與帶教人授權，沒有授權時只準備草稿。

  1. 前｜「搜尋怪怪的」
  2. 寫下現況：怎麼做會出錯
  3. 寫下驗收：怎樣算做好
  4. 後｜搭檔照著草稿能重現問題
  1. 正式流程先到練習專案的 Issues 頁，看看有沒有人回報過同一件事。
  2. 貼「擬 Issue 草稿」，請 Codex 寫。
  3. 把草稿念給搭檔聽，看他能不能照著重現。
  4. 取得授權後才建立到 GitHub，記下 Issue 編號。離線練習沿用 LOCAL-1。
擬 Issue 草稿（貼給 Codex）
看完整指令
請擬一張 Issue。標題「搜尋忽略關鍵字前後空白」。現況：搜尋「  入門  」找不到「程式入門」。驗收：有無前後空白得到同一個結果，其他搜尋行為維持既有規則。列出重現步驟、影響與測試方式。只提供文字草稿，未經我同意不要發到 GitHub。

過關畫面 搭檔只看草稿就能重現問題，並說得出怎樣算做好。正式流程記下實際 Issue 編號與網址；離線練習用 LOCAL-1。

帶教備註

好的 Issue 有三樣：可重現的步驟、可觀察的驗收條件、不在範圍內的事。建立 Issue 屬於外部操作，沒有授權時只備草稿。可以用 Issue 編號替 Codex 聊天命名，之後容易找回。

第一張任務

開一個修改分支（Branch）

分支就像把目前的版本拉出一份，專門做這張工單，不會弄亂原本的版本。前置條件：已有 Issue（離線練習為 LOCAL-1），離線練習的測試檔還在工作區。

  1. main：原本的版本
  2. 拉出一條分支
  3. issue/local-1-trim-query：這次修改專用
  4. 後｜Codex 指得出目前在哪個分支
  1. 貼「建立分支」，請 Codex 建立。
  2. 請它指出目前在哪個分支。
  3. 確認第 3 課留下的測試檔還在。
建立分支（貼給 Codex）
看完整指令
核對 repo、Issue 和工作區狀態。從最新指定基底開符合專案規則的分支。任何既有修改先核對歸屬，不要丟棄。離線小題從本機 main 建立 issue/local-1-trim-query，保留尚未提交的測試檔。完成後執行 git status -sb，用一句白話告訴我目前在哪個分支。

過關畫面 git status -sb 顯示 issue/local-1-trim-query，尚未提交的測試檔仍在。

帶教備註

團隊規則示例：分支命名 issue/<Issue 編號>-<短名稱>，從 fetch 後的最新 origin/main 建立，優先使用獨立 worktree，避免和他人的修改混在同一個工作副本。工作區若有不屬於本次任務的修改，先問清楚是誰的，不要讓 Codex 自行還原或覆蓋。

第一張任務

重現問題，再修好程式

只改一個地方，親眼看同一個測試從失敗變通過。前置條件：完成離線搜尋練習，並已在 issue/local-1-trim-query 分支上。

  1. 前｜搜尋「 入門 」找不到「程式入門」，測試失敗
  2. 只改一處：比對前去掉關鍵字前後空白
  3. 重跑同一個測試
  4. 後｜搜尋「 入門 」找到「程式入門」，測試通過
  1. 貼「先重現失敗」，確認失敗還在，並聽懂是哪一項。
  2. 貼「最小修改」，請 Codex 只改一處。
  3. 看它重跑測試：兩項都通過。
  4. 還是失敗時貼「卡住時」，先找原因再修。
先重現失敗（貼給 Codex）
看完整指令
請執行 node --test search.test.cjs，用白話告訴我哪一項失敗、為什麼失敗。先不要修改任何檔案。
最小修改（貼給 Codex）
看完整指令
只在搜尋比對前處理 query 的前後空白。先檢查既有規則，尤其是空查詢，行為要維持不變。改完執行 node --test search.test.cjs，回報改了哪幾行，以及修改前失敗、修改後通過的測試輸出。不要為了通過而修改測試的預期結果。
卡住時（貼給 Codex）
看完整指令
測試還是失敗。請先找出原因再修，不要為了通過而改測試的預期結果，也不要擴大修改範圍。回報原因、修法和重跑後的結果。

過關畫面 你能示範同一個測試：修改前失敗、修改後通過，而且說得出只改了哪一處。

帶教備註

保留「搜尋失敗到通過」的完整過程，是這門課最重要的證據。需要第二雙眼睛時，到「Agent 分工」請本機 Claude 做唯讀複核，發現交回 Codex 查證。若任務擴大成正式畫面或操作流程的變更（例如重做搜尋介面），實作前先走支線：由本機 Claude 產出實際可渲染的設計稿，負責人打開稿件走一遍並確認，Codex 才接手實作，完成後逐項對稿。已有確認稿時，核對涵蓋範圍即可，不必重畫。

第一張任務

驗證並存檔

自己親手再試一次，然後幫這次修改存一個有名字的版本（commit）。前置條件：上一課的測試已通過。這一課只做到本機，不對外送出。

  1. 對照 Issue 的驗收條件
  2. 跑檢查：通過／失敗／未跑都列出
  3. 你親手重做一次
  4. 後｜只把本次檔案存成一個 commit
  1. 貼「驗證並存檔」。
  2. 照 Codex 給的驗收方式，自己親手做一次。
  3. 把結果、畫面或測試輸出，以及還沒驗的項目，交給負責人看。
驗證並存檔（貼給 Codex）
看完整指令
請核對目前 diff 與 Issue 驗收條件，跑專案適用的檢查，列明通過、失敗或未跑的項目。只提交本次相關檔案。輸出 Issue、分支、commit、修改摘要及可重現驗收方式。這次請做到本機 commit 和預覽，後續外部操作等我指示。

過關畫面 你能親手重做一次驗收，並說得出這個 commit 放了哪些檔案。未驗的項目有如實列出。

帶教備註

有介面時，用桌機和手機實際操作，留下看得到的畫面或影片。在採用此流程的專案，依變更範圍核對 lint、type-check、build、routing smoke 與實際操作，並把預覽連結或畫面、變更摘要、結果與未驗項目交給負責人。檢查沒跑就寫沒跑，不要寫成通過。

送審

開一張審查草稿（Draft PR）

PR 是請隊友看這批修改的頁面。Draft 代表草稿。如果你用 LOCAL-1 練習，先照常擬草稿。要正式送出時，請帶教人提供 GitHub 練習專案，再用實際工單、分支及已確認的預覽接續。

  1. 負責人確認預覽
  2. 取得送出授權
  3. 推送分支，開 Draft PR

送審

通知 IT

讓對方打開 PR 一分鐘內就知道要幫忙看哪一點。前置條件：已有 PR，檢查與證據符合團隊要求。通知對象與管道以團隊設定卡為準；沒有發送授權時只準備通知稿，由你自己送出。

  1. 檢查與證據齊全
  2. 擬通知稿：連結、狀態、想問的一題
  3. 依設定卡的對象與管道送出
  4. 後｜對方知道要審什麼，意見留在 PR
  1. 貼「擬通知稿」，請 Codex 準備草稿。
  2. 對照團隊設定卡，填入對象與管道。
  3. 核對內容後由你送出，或在取得授權後請 Codex 協助。
  4. 收到審查意見，回到同一張 Issue 和 PR 修訂，重跑受影響的檢查。

看完整指令

優化

優化是讓程式更快或更好讀，但做的事情完全不變。規則只有一條：用同一把尺，先量、再改、再量。前置條件：搜尋練習的測試已全數通過並存檔。

  1. 前｜先量一次，記下數字
  2. 只改一處
  3. 跑測試：行為不變
  4. 後｜用同樣方法再量一次
  5. 有進步才保留，沒有就還原
  1. 貼「先量再改」。
  2. 看前後兩個數字，以及量測方法是否相同。
  3. 確認測試全數通過，代表行為沒變。
  4. 差異不明顯就貼「沒有進步就還原」。
先量再改（貼給 Codex）
看完整指令
請在不改變行為的前提下優化 search.cjs，依序進行：
1. 先執行 node --test search.test.cjs，確認目前全數通過。
2. 建立量測腳本 bench.cjs：用固定產生的 10 萬筆假資料與同一個關鍵字，重複執行 search 多次，記下耗時的中位數，這是修改前的數字。
3. 找出最花時間的地方，提出一個最小的修改並說明理由，然後實作。
4. 用同一份資料、同一個方法再量一次，這是修改後的數字。
5. 再跑一次測試，確認全數通過。
回報修改前後的數字、量測方法、改動範圍。差異不明顯時如實說明，不要誇大。先不要 commit。
沒有進步就還原（貼給 Codex）
看完整指令
這次優化的前後差異不明顯。請只還原你在這次練習對 search.cjs 做的優化修改，保留既有變更，保留 bench.cjs，重跑 node --test search.test.cjs 確認通過，並用一句話記下這次量到的結果。

過關畫面 你拿得出同一個方法量到的前後兩個數字，測試全數通過。沒有變好就還原，也算過關。

帶教備註

可量測、行為不變是兩個硬條件：沒有修改前的數字就不算優化，測試沒過就不算完成。量測數字會隨電腦不同而變，教材與網站不要寫死任何成效數字，請新人回報自己量到的結果。這個小題的差異可能很小，重點是練習「先量再改」的順序，以及誠實回報。正式專案的優化同樣先開 Issue、開分支，並沿用專案既有的量測方式。

  2. Codex 建立說明、搜尋程式、測試、小網頁

Agent 分工

兩個 AI 幫手一起工作時，同一時間只讓一個動手改檔案，另一個只看不改。這裡 Codex 是唯一寫入者，本機 Claude Code 做唯讀複核，由你手動把內容貼過去交棒。前置條件：已有一次存檔好的修改（「驗證並存檔」一課），本機 Claude Code 已依團隊允許的帳號與資料範圍安裝，並開在同一個專案資料夾。

  1. 你：指定 Codex 為唯一寫入者
  2. Codex：寫交棒單（輸入、產物、停止條件）
  3. 你：手動貼給本機 Claude Code
  4. Claude：唯讀複核，列出發現後停止
  5. 你：把發現貼回 Codex
  6. 後｜Codex 查證、修改、重跑測試
  1. 貼「準備交棒單」給 Codex，它寫完後會暫停修改。
  2. 在同一個專案開啟本機 Claude Code，貼「唯讀複核」，並把交棒單附在後面。
  3. 先看 Claude 回覆的資料夾與分支對不對，再看發現清單。
  4. 把發現清單附在「交回 Codex 查證」後面，貼回 Codex。
  5. 要改正式畫面時，改用「請 Claude 先畫稿」，稿件經負責人確認後才讓 Codex 實作。
